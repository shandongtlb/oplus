## 已修复并部署的两处脚本问题

1. Android mksh 会把 `exec 9>file` 的 FD 标为 close-on-exec，旧锁调用外部 flock
   报 Bad file descriptor，导致所有修改入口被阻止。改成携原参数重新 exec 脚本，
   在这次 exec 的重定向中打开 FD 9；子脚本仍核对环境标志和 inode，并继承同一锁。
   所有调用入口转交 `"$@"`。不删除锁文件、不靠固定时间判断锁释放。
2. ColorOS `wifi_on=1` 可在实际关闭时残留，旧代码还把状态文本中的
   “scanning … when wifi is enabled”误认成开机状态。现在优先精确匹配
   `cmd wifi status` 的首级状态行，再查 dumpsys，最后回退设置值。
   修复前 reset 错误恢复 Wi-Fi，框架随后把监听接口拉 DOWN；修复后 reset 保持
   关闭，等待八秒仍可正常 Probe。新增两项 Wi-Fi 状态回归。

五个生产脚本已同步手机：action、bind、monitor、公共锁、stack control。
手机原文件备份 `/data/local/tmp/op13-v81-script-backup-20260917/`。
17 项主机控制回归、身份/卸载边界及新增 Wi-Fi 状态检查通过；shell 语法和
ShellCheck（忽略动态 source 路径的 SC1091）通过。手机最终脚本 SHA 与本地一致。
设备 module.prop 暂仍显示 v8.1；运行文件已经包含本轮热修复，不能仅看版本号。

## 未通过：持续注入与快速换频时的固件 assert

`traffic-soak.txt` 原计划720轮，第约110秒、2462/20转5745/20时返回 `-EAGAIN`，
测试111.176秒结束，没有跑完。不是把该错误放宽为重试就算通过。
`soak-dmesg.txt` 的关键时间（本次 boot 秒）：

- 1382.194：2462 MHz helper ready。
- 1382.704：firmware hang，MHI进入 SYS ERROR / RAMDUMP DOWNLOAD MODE。
- 1383.016：`cmnos_assert_patched.c:604:0x8Asserted in:0x1f07818:0x1f0134c, line#1444`。
- 1383.488：`inj_wait ... control failed kind=5 host=16 fw=4294967295`，kind5为STOP。
- 1384.971：SSR自动恢复2462 MHz RX及TX helper。

本段没有发送人工SSR触发命令；主动DIAG测试的assert签名是另一处line1944。
故障发生于 helper stop 确认之前，主机停止序列与 sam 原实现一致；没有固件符号，
不能从这些地址直接断言内部根因，也没有依据用固定sleep掩盖。
恢复后pool2/1、所有队列及retained/timeouts为0，6个新Probe全部完成，捕获155 Beacon、
7个Probe回应。boot ID始终不变。最终退出后pool2/2。

追加无注入的300次同频道/带宽序列，87.625秒完成，pool次数未增加，日志无新增SSR。
这只缩小排查范围，不证明换频单独永不出错。第一次对照因接口已DOWN返回EBUSY，
确认UP后设频立即正常，不是永久锁死；接口随后DOWN的具体发起者未单独定位。
下一步优先拆分20MHz同频段/跨频段与20↔宽信道带流量场景，并取得固件assert映射，
检查helper self-peer删除/STOP确认时序。当前源码未做猜测性驱动改动。

## 另一个待查点与测试边界

旧Wi-Fi状态误判后的模式切换，在891.875秒触发cfg80211 core.c:1535 WARNING：
NETDEV_DOWN时仍有该接口的scheduled-scan请求。`hdd_stop_present_mode`的扫描清理
与PNO/cfg80211请求终止时序需专项核查；只停止固件PNO不等于释放cfg80211请求。
修正Wi-Fi状态后的reset未再出现该警告，但本轮不能宣称驱动根因已修。

未完成：已知160MHz空口接收、配套OPPO平板端共享、真正系统suspend/resume、

断线效果；未指定新自有AP，管理帧测试仅发送Probe，没有对旁边AP做deauth。

测试辅助失败均保留原日志：最初的锁测试用了本机toybox不支持的flock文件命令格式；
